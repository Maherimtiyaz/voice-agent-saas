# Voice Agent Platform

A SaaS foundation for a product that lets businesses build AI phone agents:
answer inbound calls, understand intent, call backend tools, and complete
workflows like booking appointments or creating CRM records.

**Current state: Phase 0 (auth, organizations/workspaces, dashboard shell)
plus Phase 1 (real inbound calling — Twilio + Vapi, call history,
transcripts).** Appointment booking, CRM integration, outbound campaigns,
billing, and a public API are NOT implemented — see "What has NOT been
implemented yet" below.

## Tech stack

- Next.js 16 (App Router, Turbopack) + React 19 + TypeScript
- PostgreSQL + Drizzle ORM
- Tailwind CSS v4 + hand-rolled shadcn-style UI primitives
- Auth: bcrypt password hashing + stateless JWT sessions (`jose`) in an
  httpOnly cookie
- Twilio (inbound call webhook, signature-verified) + Vapi (voice runtime,
  via the documented "phone-call-bypass" pattern)
- Vitest, with real service-layer tests run against an in-memory Postgres
  (`@electric-sql/pglite`) rather than mocks

## Architecture

### Request flow (dashboard)

```
UI (Server/Client Component)
  -> Server Action (app/actions/*)      - parses FormData, calls a service
    -> Zod validation (server/validation/*)
      -> Service (server/services/*)     - the ONLY place business rules live
        -> requireMembership() / requireCurrentContext()   - tenant guard
          -> Drizzle query (db/schema.ts) -> Postgres
```

### Voice call flow (Phase 1)

```
Customer dials a Twilio number
  -> Twilio POSTs to /api/voice/twilio/inbound (signature verified)
    -> resolvePhoneNumberForInboundCall(db, To)   <- THE tenant-identity
                                                       trust boundary: looks
                                                       up OUR phone_numbers
                                                       table by the dialed
                                                       number, nothing else
      -> phone_numbers row -> agents row (agent.vapiAssistantId)
        -> createBypassCall(): POST https://api.vapi.ai/call with
           phoneCallProviderBypassEnabled: true, assistantId, customer.number
          -> Vapi returns TwiML; we return that TwiML to Twilio as-is
            -> Twilio bridges the call to Vapi directly (we're no longer
               in the audio path)
              -> Vapi runs the conversation using the agent's system
                 prompt/voice/language
                -> Vapi POSTs status-update / transcript / end-of-call-report
                   messages to /api/voice/vapi/events (shared-secret verified)
                  -> call.service.ts updates the `calls` row and appends
                     `call_transcripts` rows
                    -> visible in the dashboard: /calls, /calls/[id]
```

We deliberately do NOT import the Twilio number into Vapi and let Vapi own
the Twilio webhook (the other documented integration path). Keeping the
Twilio webhook pointed at **our** server is what lets our own
`phone_numbers` → `agents` → `organizations` chain — not Vapi's dashboard
config — be the single source of truth for which agent handles which
number, which is what "the system must never select an arbitrary agent"
requires in a multi-tenant product.

### Agent tool framework

During a live call, the LLM can invoke a fixed set of server-side tools —
`get_customer`, `create_customer`, `check_availability`, `book_appointment`,
`create_job`, `send_sms`, `transfer_call` — via Vapi's `tool-calls` server
message. The framework this runs on (`server/tools/`) is deliberately small:

```
Vapi tool-calls webhook (message.toolCallList)
  -> the call's vapiCallId resolves to OUR calls row (organizationId, agentId)
     — this is the ONLY source of tenant identity; nothing from the tool
       call payload itself is ever trusted for that
  -> executeTool(): look up the tool by name
       -> validate rawInput against that tool's zod schema
          (an unknown tool or a schema violation never reaches a handler)
       -> run the handler with { organizationId, agentId, callId }
       -> log input, output/error, status, duration to tool_executions
          — every execution, success or failure
       -> catch any thrown error and return a generic message; the LLM
          and the webhook response never see a raw exception or stack trace
  -> results returned to Vapi as { results: [{ toolCallId, result }] }
```

This is what "the LLM must never receive unrestricted database access"
means concretely: the LLM only ever produces a `(toolName, arguments)`
pair; `executeTool` is the only path from that pair to a database
operation, and every tool handler re-scopes its own queries by
`context.organizationId` on top of that (see
`tests/server/tools-crm.test.ts` for the cross-org rejection cases this
produces — e.g. `create_job` refusing to link an appointment that belongs
to a different organization, even given a real appointment id).

Two of the tools are worth calling out specifically because they touch
real external systems and are the most abuse-sensitive:

- **`send_sms`** always sends `from` the organization's own registered
  number (resolved server-side from the call's `phoneNumberId`, never
  from tool input), and is capped at 3 successful sends per call — a
  prompt-injected or runaway conversation cannot use it to blast
  messages indefinitely.
- **`transfer_call`** always transfers to the agent's pre-configured
  `transferNumber` (set in the dashboard's Agents page, never a value
  the LLM/tool-call payload can supply) — its input schema literally has
  no destination field, so there's nothing for a rogue payload to
  override even if it tried.

`check_availability`/`book_appointment` and `create_job` are intentionally
minimal stand-ins, not real integrations — see the "Not implemented yet"
section and the comment at the top of `db/schema.ts`'s customers/
appointments/jobs block for exactly what's simplified (fixed business
hours, no external calendar, no external CRM).

### Two rules the whole codebase is built around

1. **Business logic never lives in a component, a route handler, or the
   schema file.** It lives in `server/services/*`, which takes an injected
   `Database` — that's what makes it unit-testable without a running Next.js
   server or a live Postgres instance (see `tests/db-test-helper.ts`, which
   runs the real schema DDL against an in-memory Postgres via pglite).
2. **The client — and the voice providers — are never trusted with tenant
   identity.** Every org-scoped service call re-derives membership from the
   session-verified user id, never from an id posted in a form. Every voice
   event re-derives the organization/agent from OUR OWN `phone_numbers`
   table keyed by the dialed number and OUR OWN `calls` table keyed by
   Vapi's call id — never from an `organizationId`/`agentId` that a request
   payload (or, worse, an LLM-extracted field) could claim to be. See
   `tests/server/call.service.test.ts` and
   `tests/server/phone-number.service.test.ts` for the cases this blocks
   (a real member of Org A cannot read Org B's call/agent/phone-number
   rows even with a real id).

### Authentication & sessions

Unchanged from Phase 0: bcrypt (12 rounds) password hashing, stateless
HS256 JWT session cookie (`{ userId, activeOrganizationId }`, httpOnly,
7-day expiry), `proxy.ts` doing an optimistic cookie check only — the real
authorization boundary is the service layer, on every request, every time.

### Organizations / workspaces

Unchanged from Phase 0: `User` <-> `OrganizationMember` <-> `Organization`,
many-to-many with a role per membership. No `users.organization_id`
anywhere.

## Database tables

| Table               | Purpose                                                                 | Key constraints |
|----------------------|--------------------------------------------------------------------------|------------------|
| `organizations`     | A tenant/workspace.                                                     | `slug` unique |
| `users`              | A global identity.                                                      | `email` unique |
| `organization_members` | Join table: who belongs to which org, with what role.               | unique `(org_id, user_id)`; cascade delete; `role` enum |
| `agents`             | Voice agent config: name, description, system prompt, voice config (jsonb), language, status, `vapi_assistant_id`. | `organization_id` cascade delete; `status` enum |
| `phone_numbers`      | A Twilio number the org owns, optionally assigned to an agent. `vapi_phone_number_id` is filled in once the number has been imported into Vapi (required by the phone-call-bypass API — see "Manual setup"). | `twilio_number_sid` unique; `e164_number` unique; `agent_id` nullable, `ON DELETE SET NULL` |
| `calls`              | One row per phone call. `status` is call-lifecycle state; `outcome` is a separate, nullable business-outcome summary (e.g. `appointment_booked`) set by the tool executor — never conflated with `status`. | `twilio_call_sid` unique; `vapi_call_id` unique; `agent_id`/`phone_number_id` NOT NULL, cascade delete |
| `call_transcripts`   | Transcript lines. `sequence_number` is assigned by US (not the provider) so display order survives out-of-order webhook delivery. Only "final" transcript chunks are persisted — partials are filtered as noise. | unique `(call_id, sequence_number)`; cascade delete |
| `webhook_events`     | Idempotency ledger for provider webhooks. `external_event_id` is a dedupe key WE derive (Twilio: the CallSid; Vapi: call id + message type + a hash of the payload) — neither provider hands us a documented stable event id. | unique `(provider, external_event_id)` |
| `customers`          | Minimal customer record for the `get_customer`/`create_customer` tools. NOT a real CRM. | unique `(organization_id, phone)` |
| `appointments`       | Backs `check_availability`/`book_appointment`. Availability is computed against this table on a fixed, hardcoded business-hours schedule (9am-5pm, org-wide) — NOT a real calendar integration. | `organization_id`/`customer_id`/`agent_id` cascade delete; `call_id` nullable, `ON DELETE SET NULL` |
| `jobs`               | Backs `create_job` — an internal work-order record, not a connection to any external job-management/CRM system. | `customer_id` cascade delete; `appointment_id` nullable, `ON DELETE SET NULL` |
| `tool_executions`    | Execution ledger for every tool call an agent makes — input, output or error, status, duration. This is what "log execution" means concretely; see `server/tools/executor.ts`. | indexed on `call_id` |

## Local setup

### 1. Install dependencies

```bash
npm install
```

### 2. Configure environment variables

```bash
cp .env.example .env
```

| Variable              | Required for      | Notes |
|-------------------------|--------------------|-------|
| `DATABASE_URL`         | everything         | Postgres connection string |
| `SESSION_SECRET`       | everything         | `openssl rand -base64 32` |
| `APP_URL`              | voice              | Exact public HTTPS origin this app is deployed at — must match the Twilio Voice webhook URL exactly |
| `TWILIO_ACCOUNT_SID`   | voice              | Twilio Console -> Account |
| `TWILIO_AUTH_TOKEN`    | voice              | Twilio Console -> Account. Used only to verify `X-Twilio-Signature` |
| `VAPI_PRIVATE_API_KEY` | voice              | Vapi dashboard -> API Keys |
| `VAPI_WEBHOOK_SECRET`  | voice              | A secret you choose — see step 5 below |

No real secrets are committed anywhere in this repo; `.env` is gitignored.

### 4. Run the dev server

```bash
npm run dev
```

`/` redirects to `/login` or `/dashboard` depending on session state.

### 5. Manual setup required (Twilio + Vapi)

This app never calls Twilio's or Vapi's provisioning APIs on your behalf —
Phase 1 is deliberately scoped to the *runtime* call-handling path, not
automated account setup. You need to do the following yourself:

1. **Buy or use an existing Twilio phone number** (Twilio Console -> Phone
   Numbers). Note its **Number SID** (starts with `PN`) and its E.164
   number.
2. **Point that number's Voice webhook at this app**: Twilio Console ->
   Phone Numbers -> your number -> Voice Configuration -> "A call comes in"
   -> Webhook -> `${APP_URL}/api/voice/twilio/inbound`, HTTP POST. This
   URL must exactly match `APP_URL` in your `.env`, including scheme —
   Twilio's signature covers the exact URL it requested.
3. **Import the same number into Vapi**: Vapi dashboard -> Phone Numbers ->
   Create Phone Number -> "Import Twilio" -> enter the number, your Twilio
   Account SID and Auth Token. Copy the resulting **Vapi phone number ID** —
   you'll paste this into the "Register a phone number" form in this app's
   `/phone-numbers` page. (Vapi's phone-call-bypass API requires a
   `phoneNumberId` even though Vapi isn't managing this number's Twilio
   webhook — see the code comment in
   `server/integrations/vapi/call.ts`.)
4. **Configure a Vapi Server URL credential**: Vapi dashboard -> your
   account/assistant -> Server URL -> set it to
   `${APP_URL}/api/voice/vapi/events`, and add a **Custom Credential** of
   type `X-Vapi-Secret` with a value matching `VAPI_WEBHOOK_SECRET` in your
   `.env`. Without this, Vapi will still POST to your server, but this app
   will reject every request with 401.
5. **In this app's dashboard**: create an Agent (`/agents`), click
   "Sync to Vapi" (this calls Vapi's `/assistant` API using
   `VAPI_PRIVATE_API_KEY` and stores the returned assistant id), then go to
   `/phone-numbers`, register the number from step 1 with the Vapi phone
   number ID from step 3, and assign it to the agent.
6. Call the number.

## What has NOT been implemented yet

- Real appointment/calendar integration (Google Calendar, Outlook, etc.) —
  `check_availability`/`book_appointment` work only against our own
  `appointments` table on a fixed business-hours schedule
- Real CRM integration — `customers`/`jobs` are internal records only
- A generic, user-configurable workflow engine
- Outbound campaigns, campaign queues, Redis, BullMQ
- Billing, a public API
- RAG / knowledge base
- Custom STT/TTS/voice orchestration, Twilio Media Streams
- Human handoff beyond the single fixed `transfer_call` destination,
  sentiment analysis
- Automated Twilio/Vapi provisioning (buying numbers, importing them,
  creating Server URL credentials) — all manual, see above
- Organization invites (a second member currently has to be inserted by
  hand)
- HMAC-based Vapi webhook verification (shared-secret only — see
  `server/integrations/vapi/verify.ts` for why)
- Retrying a genuinely-duplicated Twilio inbound webhook without creating
  a second Vapi call is handled for the common case (our own
  `webhook_events` dedupe on CallSid, checked before calling Vapi) but is
  not fully race-proof under concurrent delivery — there is intentionally
  no queue or distributed lock in Phase 1
- Per-tool rate limiting beyond `send_sms`'s per-call cap (e.g.
  `book_appointment`/`create_job` have no call-level or org-level
  throttling)
- A dashboard view of individual `tool_executions` rows (aggregate counts
  are on the Analytics page; the raw per-call log isn't surfaced in the
  UI yet — it's fully queryable in the database)
- The Analytics page aggregates in application code over a single
  per-organization fetch (see `server/services/analytics.service.ts`) —
  fine at Phase 1.2 call volumes, but not how you'd want it to scale to
  a large call history

## Verification performed in this environment

- `npx tsc --noEmit` (via `npm run typecheck`): **passes, zero errors**, no
  `any`/`@ts-ignore`/`@ts-expect-error` anywhere in the code.
- `npm test` (Vitest): **100/100 tests passing**, across:
  - Phase 0: password hashing, session tokens, registration/login,
    organization membership + role enforcement, agent CRUD + tenant
    isolation.
  - Phase 1 (calling): phone-number registration + duplicate-SID/duplicate-
    E.164 rejection + cross-org agent-assignment rejection; call lifecycle
    (idempotent creation, status-update transitions, end-of-call-report
    status mapping, transcript sequencing); webhook idempotency (same
    event ignored on retry, distinguished correctly by provider); Twilio
    signature verification (valid / tampered / wrong-token / missing
    cases, using the Twilio SDK's own signature generator as the test
    fixture — not a hand-rolled one); Vapi shared-secret verification;
    Vapi webhook payload validation (valid and invalid shapes for
    status-update/transcript/end-of-call-report); cross-tenant isolation
    for calls and phone numbers (a real member of Org A cannot read Org
    B's call, agent, or phone-number rows via a real id).
  - Phase 1.1 (tool framework): the executor (unknown tool, schema
    validation before the handler runs, thrown errors never leaking their
    message, every execution logged); get_customer/create_customer
    (found/not-found, idempotent on duplicate phone, cross-org isolation,
    malformed-input rejection); check_availability/book_appointment
    (correct slots on an empty day, booking removes that slot from later
    availability, double-booking refused, cross-org isolation);
    create_job (fails without an existing customer, succeeds with one,
    refuses to link another organization's appointment even given a real
    id); send_sms/transfer_call guard paths (no transfer number
    configured, malformed destination, body-length limit — all rejected
    before any Twilio API call is attempted); Vapi tool-schema generation
    covering all 7 tools.
  - Phase 1.2 (outcome + analytics): a real successful booking sets
    `appointment_booked`; a booking attempt that finds the slot already
    taken does NOT overwrite a call's existing outcome (verifies
    `success: true` alone is never enough to declare an outcome); a pure
    read (`get_customer`) never sets one; the last outcome-bearing tool
    call in a sequence wins; call-summary aggregation (status/outcome
    counts, average duration, 14-day daily volume) and tool-usage
    aggregation, both with cross-org isolation.
- `npm run build` (`next build`): **succeeds** for all 14 routes including
  the two webhook routes and the new Analytics page. As in Phase 0, this
  sandbox's network egress
  blocks `fonts.googleapis.com` (used by `next/font/google` in
  `app/layout.tsx`); the build was verified with system fonts swapped in
  temporarily, then the real font import was restored for the delivered
  code. This will build as-is with normal internet access.
- **Not verified — no live Twilio/Vapi credentials were available in this
  environment:** the actual `send_sms` Twilio Messages API call, the
  actual `transfer_call` Twilio call-redirect API call, and the full
  Twilio→webhook→Vapi-bypass round trip (same caveat as Phase 1). The
  request shapes for the SMS send and call-transfer APIs were verified
  against current Twilio documentation before implementing (both are
  long-stable, well-documented APIs: `client.messages.create` and
  `client.calls(sid).update({ twiml })`); the Vapi `tool-calls` webhook
  envelope and `{results: [...]}` response shape were verified against
  current Vapi documentation the same way. Everything that doesn't need
  live credentials — validation, authorization/isolation, logging,
  failure handling, and the guard paths that run before any external API
  call — is covered by the test suite above.
- **Twilio and Vapi API contracts were verified against current
  documentation before implementation**, not written from memory:
  - Twilio: `twilio.validateRequest`/`validateRequestWithBody` is Twilio's
    own recommended signature-verification helper
    (twilio.com/docs/usage/webhooks/webhooks-security) — this app uses it
    directly rather than reimplementing the HMAC-SHA1 scheme.
  - Vapi: Server URLs have **no authentication by default**; the
    shared-secret `X-Vapi-Secret` credential this app implements is one
    of Vapi's own four documented options (docs.vapi.ai/server-url/server-
    authentication) — not invented here. The server-message envelope
    (`{ message: { type, ... } }`) and the `status-update` /
    `transcript` / `end-of-call-report` field shapes match
    docs.vapi.ai/server-url/events and current Vapi-published examples.
    The phone-call-bypass request shape
    (`phoneCallProviderBypassEnabled`, `phoneNumberId`, `assistantId`,
    `customer.number`, reading back `phoneCallProviderDetails.twiml`)
    matches Vapi's own support-provided example for this exact
    Twilio-inbound-to-Vapi pattern.
  - **What could NOT be verified**: no live Twilio or Vapi account was
    available in this environment, so the actual HTTP round-trip to
    `POST https://api.vapi.ai/call` (and `/assistant`) has not been
    exercised against a real account. The request/response shapes are
    implemented per current documentation and community-verified
    examples, isolated behind `server/integrations/vapi/*` specifically
    so they're easy to adjust in one place if a live call surfaces a
    mismatch. Test it against a real Twilio number + Vapi account before
    relying on it in production.
- Database: no live Postgres instance was available, so `db:push`/
  `db:generate` have not been run against a real database. The identical
  schema DDL (mirrored by hand in `tests/db-test-helper.ts` — see that
  file's header comment) was exercised throughout the test suite against
  a real Postgres-compatible engine (pglite), including every unique
  constraint, foreign key, and cascade-delete behavior this README
  documents.
